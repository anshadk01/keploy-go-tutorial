> A beginner-friendly, developer-focused guide to capturing real-world API traffic, generating deterministic test suites, and mocking MongoDB with zero code changes.

<h2 id="overview">1. The Go Testing Dilemma & Keploy's Promise</h2>

If you build microservices in Go using popular frameworks like **Gin** alongside **MongoDB**, you know that writing integration tests is usually where developer joy goes to die.

Every engineering team eventually gets trapped between two frustrating extremes:

1. **Brittle Unit Mocks**: You wrap `*mongo.Client` behind custom Go interfaces (`type Database interface`), generate mocks with tools like `mockgen` or `testify`, and spend hours handcrafting mock expectations (`mockDB.On("InsertOne", ...).Return(...)`). The second you adjust your MongoDB aggregation query or add an index, your mocks silently go out of date.
2. **Heavy Docker Integration Tests**: You spin up ephemeral database containers via `testcontainers-go` or Docker Compose. These tests are notoriously slow, require constant database state cleanup between runs, and produce frequent flaky failures in CI pipelines due to network timeouts.

<Callout type="aha" title="The Keploy Paradigm Shift">
  **Keploy solves this by moving testing from application code down to the network transport layer.** 
  
  Using Linux **eBPF** (Extended Berkeley Packet Filter), Keploy passively observes incoming HTTP calls and outgoing MongoDB TCP packets. It records both sides of the conversation into clean, human-readable YAML files, allowing you to replay regression tests hermetically—**without running MongoDB at all**.
</Callout>

### Core Value for Teams & Leaders

- **For Software Engineers**: You write zero mock structs, zero interface wrappers, and zero lines of test boilerplate. You simply run your app and test it by using it.
- **For Engineering Managers & Tech Leads**: Test suites run in seconds in GitHub Actions without managing database containers, slashing CI/CD build minutes and server costs.
- **For Product & QA Teams**: Automated regression tests represent real customer traffic and actual production queries, not idealized developer assumptions.

<h2 id="mental-model">2. Architecture & Mental Model</h2>

Before opening a terminal, let's look under the hood. Keploy operates in two primary phases: **Record Mode** and **Test Mode**.

<ArchitectureDiagram />

### How Transport-Level Interception Works

Unlike traditional mocking libraries that modify functions inside your Go codebase, Keploy operates as an intelligent sidecar on your operating system:

1. **Ingress Capture**: Keploy binds to your application's ingress port (e.g., `:8080`) to capture incoming HTTP requests, headers, and response bodies.
2. **Egress Interception**: When your Go code initializes `mongo.Connect(...)` on port `27017`, Linux eBPF socket filters route the TCP stream through Keploy's proxy engine. Keploy reads the MongoDB wire protocol (`OpMsg` / opcode 2013) and records both the query and the database response.
3. **Hermetic Replay**: In test mode, Keploy starts your compiled Go binary, simulates the recorded HTTP calls, and answers every MongoDB query with the recorded mock data. **MongoDB is completely shut off.**

<Callout type="why" title="Why this matters">
  Your Go code does not need any SDK or instrumentation. It uses its standard MongoDB driver, connects to `localhost:27017`, and receives exact byte-for-byte protocol responses from Keploy.
</Callout>

<h2 id="inspect-artifacts">6. Step 2: Under the Hood: Inspecting Real YAML & Mocks</h2>

Keploy created a `./keploy/` directory in your project root containing the captured test suite. Explore the exact generated artifacts below:

<FileTree />

### Deep Dive: `test-1.yaml` (HTTP Contract)

Notice how Keploy records the exact HTTP interaction:
- **`spec.req`**: The incoming HTTP method, URL, headers, and body (`{"url": "https://google.com"}`).
- **`spec.resp`**: Expected status code `200 OK`, headers, and response body.
- **`assertions.noise`**: This is critical! Keploy automatically detected that `body.ts` (timestamp) and `header.Date` change on every run. By placing them in the `noise` array, Keploy ignores dynamic timestamps during assertion matching, preventing flaky test failures.

### Deep Dive: `mocks.yaml` (MongoDB Wire Mock)

Notice the `mocks.yaml` entry:
- **`Opcode: 2013`**: This corresponds to MongoDB's modern `OpMsg` wire protocol opcode.
- **`sections`**: Captures the exact BSON document upserted into the `url-shortener` collection.
- **`responses`**: Captures the server acknowledgment (`ok: 1.0`, `n: 1`).

<Callout type="aha" title="The 'A-Ha!' Moment: Wire-Protocol Mocking">
  Notice that Keploy did not mock a Go struct or an interface method. It mocked the **underlying TCP protocol payload**. This means regardless of whether your team updates the MongoDB driver, refactors repository code, or changes internal functions, the tests remain 100% valid as long as the database protocol contract holds!
</Callout>

<h2 id="aha-moments">10. DevRel "A-Ha!" Moments</h2>

During hands-on quickstarts, developers consistently encounter three transformative epiphanies:

### 1. Transport-Level vs. Application-Level Mocking
Traditional mocking libraries live in application space; if your function signature changes, all your mock tests break. Keploy lives in network space. It doesn't care how you refactor your Go structs as long as the external HTTP contract and database queries produce the expected outcome.

### 2. Zero-Database CI/CD is Real
In standard enterprise setups, setting up test databases in GitHub Actions involves complex service containers, migration scripts, and seed files. With Keploy, the `mocks.yaml` file travels with your Git repo, allowing tests to run in hermetic isolation in seconds.

### 3. Automatic Noise Detection
Nothing kills team trust in automated testing faster than flaky tests caused by `time.Now()` or randomized UUIDs. Keploy's automatic detection of `noise` fields in `test-1.yaml` keeps test assertions robust without manual regex tuning.

<h2 id="troubleshooting">11. Troubleshooting & Common Pitfalls</h2>

When running Keploy locally or in containerized environments, keep these common solutions in mind:

| Symptom / Error | Root Cause | Solution |
| :--- | :--- | :--- |
| `connection refused` on `:8080` during `keploy test` | The Go application has not finished compiling or binding the port before Keploy begins firing replay requests. | Add `--delay 10` or `--delay 15` to give the Go runtime and DB pool adequate boot time. |
| `operation not permitted` / eBPF load failure | Keploy requires elevated Linux network capabilities to attach socket filter hooks. | Always prefix commands with `sudo -E env PATH=$PATH keploy ...` on Linux/WSL2. |
| `bind: address already in use :27017` | An existing local MongoDB service or orphaned Docker container is already holding port 27017. | Run `docker ps` and `docker stop <id>`, or check `lsof -i :27017`. |
| `no test cases found in keploy/` | HTTP requests were made before Keploy finished initializing or sent to the wrong port. | Wait for the `Keploy is actively capturing...` log line before sending cURL requests. |
| Windows native limitations | Windows kernel does not natively support Linux eBPF socket filters. | Run Keploy inside **WSL2 (Ubuntu)** or via Keploy's Docker container mode. |

<h2 id="cicd-integration">12. Production CI/CD Pipeline</h2>

Here is a production-ready **GitHub Actions workflow** (`.github/workflows/keploy.yml`) that runs your regression tests on every Pull Request **without any database container**:

<CodeBlock
  language="yaml"
  filename=".github/workflows/keploy.yml"
  showLineNumbers={true}
  code={`name: Keploy Zero-Code Regression Tests

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Set up Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true

      - name: Download Go Dependencies
        run: go mod download

      - name: Install Keploy CLI
        run: curl --silent -O -L https://keploy.io/install.sh && bash install.sh

      - name: Run Hermetic Keploy Tests (No Mongo Needed!)
        run: |
          sudo -E env PATH=$PATH keploy test -c "go run main.go handler.go" --delay 10
`}
/>

### Summary Cheat Sheet

```bash
# 1. Record tests with running application & MongoDB
sudo -E env PATH=$PATH keploy record -c "go run main.go handler.go"

# 2. Replay all test sets (MongoDB can be stopped!)
sudo -E env PATH=$PATH keploy test -c "go run main.go handler.go" --delay 10

# 3. Replay specific test set
sudo -E env PATH=$PATH keploy test -c "go run main.go handler.go" --delay 10 --testsets "test-set-0"
```
